# `.ncm` 容器格式说明

`.ncm` 没有公开规范。以下布局由本项目从真实文件解析、并用自带的写入器（`NcmWriter`）反向验证得到——
所有结论都能通过「写入 → 读回」的单元测试复现。

---

## 一、整体布局

```
偏移        长度            内容
0x00        8               "CTENFDAM" 魔数
0x08        2               保留（01 70）
0x0A        4               密钥块长度（小端）
0x0E        keyLen          密钥块
            +4              元数据块长度（小端）
            +metaLen        元数据块
            +4              CRC32
            +5              保留字节
            ...             负载区（见第二节）
```

## 二、密钥块

```
逐字节 ^ 0x64
  → AES-128-ECB 解密（固定密钥 hzHRAmso5kInbaxW）
  → 去 PKCS#7 填充
  → 去掉 17 字节前缀 "neteasecloudmusic"
  → 每个文件各自的音频密钥
```

## 三、元数据块

```
逐字节 ^ 0x63
  → 去掉 22 字节前缀 "163 key(Don't modify):"
  → base64 解码
  → AES-128-ECB 解密（固定密钥 #14ljk_!\]&0U<'( ）
  → 去填充
  → 去掉 6 字节前缀 "music:"
  → UTF-8 JSON
```

JSON 里包含曲名、艺人、专辑、时长、位深、码率、原始格式、内嵌封面等字段。

## 四、音频负载

音频用一个**由密钥派生、周期为 256 字节**的密钥流按位异或。参考实现的每字节密钥流做了 4 次关联查表：

```c
j = (i + 1) & 0xFF;
mask = box[(box[j] + box[(box[j] + j) & 0xFF]) & 0xFF];
```

关键点在于 **`j` 只取决于 `i mod 256`**，所以整条密钥流就是一个 256 字节的循环表。

本项目据此**预计算掩码表**，解密退化成一次查表异或（`NcmKeystream`），并且用单元测试锁住
「分块解密的结果 == 整体解密的结果」这一性质——这条性质让解密流可以随机寻址，不必从头解到尾。

## 五、负载区的三种布局

| 布局 | 结构 | 出现场景 |
|---|---|---|
| `Standard` | `[音频]` | 旧版下载 |
| `AfterEmbeddedImage` | `[uint32 封面长度][封面图][音频]` | **当前主流**，封面以明文内嵌 |
| `Scanned` | 靠签名扫描定位 | 兜底 |

`AfterEmbeddedImage` 是本项目在分析真实沉浸声文件时发现的：文档化的 9 字节尾部之后并不是音频，
而是一段**明文 JPEG**。解析器先做结构判断（`uint32` 长度 + 图片魔数是否自洽），再对音频起点做签名校验。

> **一批 18 个真实样本全部是 `AfterEmbeddedImage` 布局。**
> 只按旧文档实现会把它们全部解错。

`Scanned` 兜底只接受**无歧义签名**（FLAC / `ftyp` / OggS / RIFF / ID3 / ADTS）。
原因是杜比的两字节同步字（`0B 77`）在 14 MB 数据里会偶然出现几十次，用它定位音频起点会产生误判。

## 六、CRC32

元数据块与负载之间有一个 CRC32 字段。本项目目前**不校验**它：真实文件中该字段的算法与覆盖范围
尚未确认，把它当作校验位会在合法的第三方文件上产生假阳性。

## 附：关于「环绕声用 E-AC-3 写入 FLAC」的澄清

社区里有「网易云的环绕音乐是把 E-AC-3 写进了 FLAC」的说法。实测结论是：**现象真实，但编码不是 E-AC-3。**

被命名为 `.flac` 的沉浸声文件，实际内容是 **MP4 容器 + AVS3-P3（Audio Vivid / 菁彩声）编码**：

```
magic: 00 00 00 1C 66 74 79 70 69 73 6F 6D   [....ftypisom]
codec_tag_string=av3a   channels=12   sample_rate=44100
format_name=mov,mp4,m4a,3gp,3g2,mj2
```

也就是说，文件确实被**错误地标成了 `.flac` 扩展名**，但里面的编码是 AVS3-P3，不是 E-AC-3。
这解释了为什么播放器打不开这些「FLAC」文件。

内置的 `libncmdump.dll` 是原生 C++（使用 TagLib），只导出 `CreateNeteaseCrypt` / `DestroyNeteaseCrypt`，
同样不包含 E-AC-3 或 PCM 处理。**没有任何参考实现支持 EAC3/PCM**，实测样本里也没有出现过这两种编码。
