# SignPath 接入指南

CI 里的 Windows 签名走 **SignPath**。签名管线已经接好并随仓库发布，
但 SignPath 那一侧的账号、项目、策略只能在他们的网页后台建立 —— 这份文档是那部分的操作步骤。

配置完之前，工作流会**整体跳过**签名步骤并正常构建，所以仓库现在就是可用的，只是产出未签名。

---

## 为什么是 SignPath，而不是 Certum

2023 年 6 月起，CA/Browser Forum 要求**公开可信的代码签名证书必须把私钥放在硬件或云端 HSM 里**。

| 方案 | 私钥在哪 | GitHub 托管 runner 能用吗 |
|---|---|---|
| **SignPath** | SignPath 的 HSM | ✅ 能 —— CI 只提交请求，从不接触私钥 |
| Certum SimplySign | Certum 云端，通过登录的桌面客户端暴露 | ❌ 不能 —— 需要交互式登录和常驻客户端 |
| Certum 导出 pfx | —— | ❌ 公开可信证书**根本无法导出成 pfx** |

所以 Certum 留作[本机签名](README.md)的路子，CI 用 SignPath。

## 一、申请 SignPath Foundation（开源免费）

<https://signpath.org/> 为开源项目提供**免费**的代码签名。需要满足：

- 仓库**公开** ✅ `112012201/ncmforge` 是公开仓库
- **OSI 认可的开源许可证** ✅ GPL-3.0
- 项目处于活跃维护状态 ✅

申请时准备好：仓库地址、许可证、项目简介、以及这个程序的用途说明
（网易云音乐 NCM 容器转换器，自带 .NET 运行时）。

> 审核由 SignPath 人工完成，需要等。**在此之前不需要改任何代码** —— 先把仓库变量留空即可。

---

## 二、在 SignPath 后台建四样东西

审核通过后，登录 <https://app.signpath.io/>，记下每个 slug（后台里显示为 “Slug”）。

### 1. Organization ID

在组织设置页。是一个 **GUID**，形如 `00000000-0000-0000-0000-000000000000`。
填进仓库变量 `SIGNPATH_ORGANIZATION_ID`。

### 2. Project（项目）

新建一个项目，名字随意（建议 `ncmforge`），slug 就是 `SIGNPATH_PROJECT_SLUG`。
把刚建好的 Certificate 和下面的 Signing Policy 关联进去。

### 3. Signing Policy（签名策略）

新建一条策略，slug 就是 `SIGNPATH_POLICY_SLUG`。
它决定用哪张证书、以及签名请求是否需要人工批准。

> **建议**：先用需要**人工批准**的策略跑一次，确认提交的产物正确，再改成自动批准。
> 一旦自动批准，任何满足条件的工作流都能拿到签名，这是安全边界。

### 4. Artifact Configuration（产物配置）×2

仓库里已经写好了两份，**直接复制粘贴**进 SignPath 的新建 Artifact Configuration 里：

| 建这个 | 内容来自 | 建议 slug | 填进变量 |
|---|---|---|---|
| 二进制配置 | [`installer/signpath/binaries.xml`](../installer/signpath/binaries.xml) | `ncmforge-binaries` | `SIGNPATH_CONFIG_SLUG` |
| 安装包配置 | [`installer/signpath/installer.xml`](../installer/signpath/installer.xml) | `ncmforge-installer` | `SIGNPATH_INSTALLER_CONFIG_SLUG` |

两份配置里用到的写法都带注释解释了原因，简单说：

- 根元素必须是 `<zip-file>`，因为 `actions/upload-artifact` 会把上传的东西**再打一层 zip**。
- 安装包配置**只签安装包本身**，伸不进去。Inno Setup 把负载压缩存放，SignPath 无法打开里面的 PE 文件 ——
  所以工作流是**先签程序 → 再用已签名的程序构建安装包 → 最后签安装包**，顺序不能颠倒。

---

## 三、建 API Token

后台 → 用户设置 → API Tokens，建一个具备 **submitter** 权限的 token，
作用范围限定到刚建的 project + signing policy（不要给组织级全权限）。

填进仓库 **Secret** `SIGNPATH_API_TOKEN`。

---

## 四、安装 SignPath GitHub App

<https://github.com/apps/signpath> → 授权给 `ncmforge` 仓库。

这一步本身不是签名必需的，但 SignPath 的**审计日志评估**（开源项目的完整性策略）需要它。

---

## 五、在仓库里填变量

Settings → Secrets and variables → Actions：

**Variables**（不是 Secret）：

```
SIGNPATH_ORGANIZATION_ID        = <组织 GUID>
SIGNPATH_PROJECT_SLUG           = <项目 slug>
SIGNPATH_POLICY_SLUG            = <策略 slug>
SIGNPATH_CONFIG_SLUG            = ncmforge-binaries
SIGNPATH_INSTALLER_CONFIG_SLUG  = ncmforge-installer
```

**Secrets**：

```
SIGNPATH_API_TOKEN              = <API token>
```

填完**不需要改代码**。下次发布时签名步骤会自动激活 —— 触发条件就是
`SIGNPATH_CONFIG_SLUG` 非空。

## 六、验证（顺带回答根证书信任的问题）

你提到过「Windows 未对 SignPath 的根证书启用信任」，但记不清当时的具体情况。
签名跑通后用下面几条**实测**，不要靠印象：

```powershell
# 1. 签名是否存在且有效
Get-AuthenticodeSignature .\NcmForge.exe | Format-List Status, StatusMessage

# 2. 证书是谁签发的、链到哪个根 —— 这一条直接回答根信任问题
$s = Get-AuthenticodeSignature .\NcmForge.exe
$s.SignerCertificate | Format-List Subject, Issuer, NotBefore, NotAfter
$s.SignerCertificate | ForEach-Object { $_.ChainStatus }
(New-Object System.Security.Cryptography.X509Certificates.X509Chain).Build($s.SignerCertificate)

# 3. 时间戳是否在（没有它，证书一到期签名就全部失效）
$s.TimeStamperCertificate | Format-List Subject, Issuer
```

判断标准：

- `Status` 必须是 **`Valid`**。`UnknownError` 通常就是链不受信任。
- `ChainStatus` 为空 = 链完整且受信任；出现 `UntrustedRoot` 才是真的根不被信任。
- 若确实出现 `UntrustedRoot`，把 `$s.SignerCertificate.Issuer` 发我，我来查是哪张根、
  以及是证书本身的问题还是那台机器的根存储太旧。

**用命令行验安装包内部也一样**（对安装包和 zip 里解出来的 exe 分别跑一遍）：

```powershell
Get-AuthenticodeSignature ".\NcmForge-<版本>-win-x64-setup.exe" | Select-Object Status
```

## 排错

| 现象 | 原因 |
|---|---|
| 签名步骤直接跳过 | `SIGNPATH_CONFIG_SLUG` 变量没填，或填错了名字 |
| `The artifact configuration does not match` | 上传的产物结构与配置不符。确认 `binaries.xml` 里的 `cli/ncmforge.exe` 路径与打包布局一致 |
| `origin verification failed` | 提交签名请求之前的 job 不是跑在 GitHub 托管 runner 上。开源项目强制要求托管 runner |
| `Insufficient permissions` | API token 的权限范围没覆盖 project + policy，或用户没有 submitter 角色 |
| 签名请求一直 pending | 策略设置成了需要人工批准，去 SignPath 后台点批准 |
